## 一、职责图（完整版）

评审期留下的图缺 Runner（当时标注"未来 Runner"）。R3 落地后补全，这是当前权威分层：

```
业务 Adapter（转换，不执行）
      ↓ 协议 Task
TaskRepository（submit 幂等 / save 原子 / update 回读式）
      ↓ record
QueueScanner（inbox 三验：Schema+Hash+READY → 认领移入 tasks/claimed/）
      ↓
Runner（状态门控 → 幂等跳过 → validate_input → execute → validate_output
        → 检查点+状态【单次原子写】→ 失败分类重试）
      ↓                ↑ WorkerResult（含 artifacts 多产物）
BaseWorker 三段契约 ←—— 业务 Worker 实现（Hunyuan3D/Blender/…）
      ↓
CheckpointManager（七项检查点：版本/输入Hash/配置Hash/输出Hash/存在性…）
      ↓
Storage（一切 IO 的唯一出口，二进制安全；Drive 后端 R4+）
      ↓
Publisher（R4 待建：八步安全发布，PUBLISHED 最后写）
```

依赖方向（谁 import 谁，单向不可逆）：

```
GS adapters/ ──→ pipeforge（Runner/Repository/…）──→ protocol/schemas
业务 Worker  ──→ BaseWorker 契约
反向依赖：不存在。PF 内部零 GS 概念，stage_key 等业务名全部参数化。
```

**职责红线表**（谁不做什么，违反必返工）：

| 层 | 只做 | 绝不做 |
|---|---|---|
| Adapter | 协议转换、稳定映射、审计 | 执行任务、伪造业务字段、改原件 |
| TaskRepository | 台账写入门（submit/save/update） | 业务逻辑 |
| QueueScanner | 提交协议验收与认领 | 执行 |
| Runner | 单阶段编排、失败分类、原子持久化 | 跨阶段调度（R4）、Worker 内部逻辑 |
| Worker | 三段执行 | 碰 Repository/状态/发布标记/attempt 计数 |
| CheckpointManager | 检查点写与验证 | attempt 计数（Runner 独占） |
| Storage | IO 抽象 | 协议语义 |

## 三、踩坑与修复目录（按层分类）

> 格式：**症状 → 根因 → 修复 → 预防**。都是实付学费，开发前扫标题即可。

### 3.1 协议层（schema × 运行时）

**P01 · schema 禁止 checkpoint_data，运行时必须要它**
- 症状：带检查点的任务过不了自身 validate；stage_valid() 却要求读 checkpoint_data。
- 根因：schema 阶段对象 additionalProperties:false 与运行时读者从未对照——静态自检测不出这类矛盾。
- 修复：阶段对象改 anyOf[空对象, 完整对象(含 checkpoint_data 自由对象)]，结构由 stage_valid() 语义校验。
- 预防：**schema 每次改动必须跑双形态 example 的 roundtrip 测试**（test_stage_forms_both_accepted / test_stage_valid_checkpoint_roundtrip 为此存在）。

**P02 · stages 双形态之争**
- 评审裁"完整对象"、协议规范示例是空 {}、代码两处都要 → 最终两阶段式：初始空、执行后完整。
- 预防：冲突裁决前先跑代码事实，别只对文档。

### 3.2 内核层（Repository / Scanner）

**P03 · update() 丢内存状态**
- 症状：Runner 推进后的任务状态全被还原。
- 根因：update() 从磁盘重读再改，调用方内存里的推进被静默丢弃。
- 修复：新增 save()（校验+原子写整个 dict，调用方拥有变更）；Runner 持久化点一律 save。
- 预防：**有内存权威副本时用 save，需要乐观回读时才用 update**。

**P04 · 认领防重放语义**
- record 丢失 + 目录已在 claimed → 重放 inbox 允许重认领（record 是权威，目录不是）。
- Scanner 五路径测试（happy/缺READY/哈希不符/ID不符/重放）必须保持全绿。

### 3.3 Runner 层

**P05 · 失败路径在 PENDING 态非法转换**
- 症状：PENDING -> RETRY_WAIT/FAILED 全线炸（6 测试同挂）。
- 根因：validate_input 拒绝时任务还没推进到 RUNNING，状态机无此直接边。
- 修复：_fail() 入口先把 PENDING 觅范化为 RUNNING。
- 预防：**任何状态写入前先查 ALLOWED_TRANSITIONS**；失败路径尤其要考虑"从未 RUNNING"的情况。

**P06 · attempt 双计数**
- 症状：重试一轮 attempt=3（应为 2）。
- 根因：Runner 步骤3 自增后，CheckpointManager.write 里又 +1。
- 修复：Runner 独占计数；CM 仅在 slot 无 attempt 键时补 1（兼容独立使用）。
- 预防：**计数职责写进职责表**，新增写 attempt 的代码先对照。

**P07 · 错误码映射双点执行丢标记**
- 症状：未知码 WEIRD_CODE 映射成 OUTPUT_INVALID 后 [unmapped] 标记消失。
- 根因：调用点 map 一次、_fail 内又判一次，第二次判断时已是合法码走了"原文"分支。
- 修复：映射收拢到 _fail() 单点，映射改变码时打 [unmapped:x->y] 前缀。
- 预防：**同一语义的转换只能有一个实现点**。

### 3.4 Worker / 存储层

**P08 · 二进制资产炸 UnicodeDecodeError**
- 症状：MockWorker 读真实 PNG 当场崩。
- 根因：Storage 只有 read_text/write_text；此前全部测试用文本文件，掩盖缺口。
- 修复：补 read_bytes/write_bytes（ABC + Local 实现）。
- 预防：**测试必须包含真实二进制资产**——E2E 用真 ref.png 才炸出这个洞，文本-only 测试给假安全感。

**P09 · 包内相对导入循环**
- 症状：from . import protocol 在 pipeforge.runner 包里解析到自身 → circular import。
- 修复：子包内引用顶层模块一律 from .. import protocol。
- 预防：新增子包照抄 core/ 的导入样式。

### 3.5 Adapter 层（GS 接入）

**P10 · 迁移元数据进不了任务文档**
- 根因：task schema root additionalProperties:false（实测确认）。
- 修复：sidecar 注册表（migration_registry.json）存映射+source_sha256+审计警告。
- 预防：**任何附加元数据默认走 sidecar**。

**P11 · hash() 生成序号跨进程不稳定**
- 根因：Python hash() 每进程加盐。
- 修复：job_id 尾部数字组确定性推导（_derive_seq），跨进程落盘探针锁死。
- 预防：**一切 ID/序号生成必须确定性**；跨进程验证用落盘脚本，别用 python -c 内联（引号地狱）。

**P12 · 不伪造业务字段**
- legacy geometry 不合 config.clean → 进审计不进 config；.blend source → 诚实拒绝；config.model 由提交方补齐，adapter 不代填。

### R5.3 交付（2026-11-22 晚，Colab Pull 5/5）

`adapters/backends/colab_backend.py`（本地侧）：submit=向 `queue/inference/` 原子写请求文件（以 idempotency_key 为文件名→天然幂等，同 key 重放=同文件）；get_status=读 Agent 进度文件；fetch=读 Agent 写回的产物；cancel=仅删未认领请求（尽力而为）。**零 Colab API、零浏览器自动化**——本地与 Agent 只通过共享 Storage 协作。

新坑：
